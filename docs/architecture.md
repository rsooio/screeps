# Screeps 殖民地控制架构设计

版本：0.3（实现版）
状态：已实现，控制律已落地（消耗速率模型）

## 1. 概述

本系统是 Screeps 殖民地（多 creep 协作）的自治控制架构。设计目标是让一组无角色、无固定分工的 creep 在**需求驱动**下涌现出稳定的劳动力分工，并能在房间状态变化（能量缺口、建造需求、等级提升）时平滑迁移产能。

架构类型：**黑板架构（Blackboard Architecture）**，配以**边际效用分配**作为控制律。

```
┌───────────────────────────────────────────────────────┐
│                     房间状态（感知）                  │
│      spawn/extensions 能量、工地、控制器、source      │
└──────────────────────┬────────────────────────────────┘
                       │ 声明（declareDemands，每 tick）
                       ▼
┌───────────────────────────────────────────────────────┐
│              需求黑板 Demand 清单（tick 内临时）      │
│        { action: "deliver"|"build"|"upgrade",         │
│          targetId, roomName }                         │
└──────────────────────┬────────────────────────────────┘
                       │ 调度（reconcile，差分增删）
                       ▼
┌───────────────────────────────────────────────────────┐
│           任务黑板 Memory.tasks（持久化）             │
│        { id, action, targetId, roomName }             │
└──────────────────────┬────────────────────────────────┘
                       │ 分配（allocate，效用最大化）
                       ▼
┌───────────────────────────────────────────────────────┐
│              Creep 执行器（EXECUTORS 表）             │
│      deliver / build / upgrade —— 按动作分发          │
└───────────────────────────────────────────────────────┘
                       │ 状态变化（能量流动）
                       ▼
                    房间状态（闭环反馈）
```

## 2. 设计原则

1. **需求与任务分离**：设施只声明"我需要什么"（需求，无状态、每 tick 重算）；任务队列是调度产物（持久化）。执行者不感知需求来源，需求不感知执行者。
2. **无角色概念**：任务描述"对什么目标做什么动作"，执行者能力由**动作 → 能力映射表**（单一事实源）判定，不按"采集者/建造者"命名。
3. **无硬编码容量**：执行者数量由边际效用递减自然饱和，不在任何地方写死上限。
4. **决策分层**：战略（生产什么）→ 战术（发布/分配）→ 操作（动作执行）三层解耦，各层频率与信息粒度不同。
5. **闭环控制**：需求即误差信号，且误差以**能量消耗速率**（energy/tick，流）量化而非绝对存量——需求强度反映"多快被消耗"，不反映"缺了多少"。
6. **黑板无所有权**：任务只有“被谁执行”的瞬时统计（每 tick 从执行者反查），无占用状态，死亡执行者自动消失，无清理逻辑。
7. **执行层滞回统一**：能量状态（采集中/工作中）用同一个两态滞回状态机驱动所有动作——满载转工作、耗尽转采集。动作在控制层面不分类（一次清空与逐 tick 消耗落在同一状态机内），新动作零成本接入。

## 3. 控制回路（每 tick）

```
① 感知     读取房间状态（结构能量、工地、控制器、source 位置）
② 声明     declareDemands：遍历可接收能量的结构，按**消耗速率**声明 deliver 需求；
            遍历工地 → build 需求；控制器 → upgrade 需求
            - spawn 生产中：rate = 剩余生产消耗 / needTime（生产瞬时消耗均摊）
            - 结构空闲未满：rate = PREP_RATE（备产预期）
            - 满：rate = 0（不声明需求）
③ 调度     reconcile：需求与任务队列差分
            - 需求存在而任务缺失 → 发布（展开能力映射）
            - 需求消失（结构满/工地完成）→ 回收任务
④ 分配     allocate：idle creep 按效用函数选择任务
⑤ 执行     EXECUTORS[action](creep, task)：操作层动作，由滞回状态机驱动
            （见 5.4）
⑥ 反馈     能量流入流出改变结构状态，进入下一 tick 的①
```

信息流单向（状态 → 需求 → 任务 → 执行 → 状态），无跨层引用；各层间以黑板（需求清单/任务队列）解耦。

## 4. 决策层次

| 层次 | 决策内容                                   | 频率                | 信息               | 实现                     |
| ---- | ------------------------------------------ | ------------------- | ------------------ | ------------------------ |
| 战略 | 生产哪个 creep（body）、何时生产、是否扩张 | 每 tick（低频影响） | 任务效用、能量存量 | `decideSpawn`            |
| 战术 | 需求声明、任务增删、执行者分配             | 每 tick             | 房间状态、效用函数 | `reconcile` / `allocate` |
| 操作 | 采集、移动、转移、建造、升级               | 每 tick             | 任务目标、自身状态 | `EXECUTORS`              |

战略层通过"任务边际效用仍为正"感知产能需求——战术层不向战略层发指令，战略层只观察黑板（弱耦合）。

## 5. 效用模型（控制律）

### 5.1 效用函数（价值与偏好分离）

控制律的关键分解：**价值决定可行性，距离决定偏好**。

```
value(task, holders, rate) = basePriority(action)
                             + rate(action) × RATE_WEIGHT     // 消耗速率加权（仅 deliver）
                             - crowdingCost(action, holders)
utility(creep, task)       = value - distanceCost(creep, task)
```

- **value（拥挤价值）**：决定“值不值得加执行者”。value < 0 = 拥挤饱和，分配器不再加人（停止条件只看 value，不看 utility）。
- **rate（消耗速率）**：需求强度 = 能量消耗速率（流）而非绝对缺口量（存量）。rate 越高价值越高，且**抬高拥挤饱和点**——生产中 spawn（rate≈17）可容忍 5 人，备产（rate=10）第 5 人自动不分配。
- **utility（完整效用）**：决定“选哪个任务”。距离只影响排序，不参与可行性判断——否则兜底任务会因距离被打穿（controller 距 spawn 20+ 格时 upgrade 的 utility 为负，creep 宁可 idle 也不升级）。

| 项           | 含义          | 特性                                                          |
| ------------ | ------------- | ------------------------------------------------------------- |
| basePriority | 需求紧急度    | deliver > build > upgrade（能量缺口最紧急，升级持续兜底）     |
| distanceCost | 运输/移动成本 | 排序偏好；源侧动态（最近 source），目标侧固定                 |
| crowdingCost | 产能边际递减  | deliver 陡峭（source 再生有限）；upgrade 平缓（多人持续有效） |

### 5.2 边际效用与动态平衡

任务对第 N 个执行者的边际效用（rate 固定时）：

```
marginal(task, n) = basePriority + rate×RATE_WEIGHT - crowdingCost(task, n)
```

- **deliver**：`crowdingCost` 递增斜率大 → 第 1 人效用高，第 N 人效用趋零；且饱和点随 rate 浮动（生产时允许多人，备产时收敛）——执行者数量由"消耗速率 × 采集产能"自然调节，**无需容量上限**。
- **upgrade**：`crowdingCost` 斜率小 → 始终有正边际效用 → 吸收一切剩余产能（兜底任务）。

平衡条件（稳态）：

```
marginal(deliver, n_d) ≈ marginal(upgrade, n_u)
```

即系统自动把产能分配到"两种任务边际效用相等"的点——与传统经济学中的边际效用均衡一致。该平衡点是涌现的，任何硬编码容量都无法表达其随房间状态（source 数、body 配置、能量缺口）变化的动态性。

### 5.5 基础设施：矿工（高成本低数量）

矿工是**基础设施**（固定产能节点，语义类似 source），不是任务经济的一部分：

- **不参与任务分配**：矿工由 spawn 决策维护（`maintainMiners`），行为固定（站在 source 旁采集，无 CARRY → 能量自动掉落），无 taskId
- **部署是投资决策**（硬编码门槛，经参数扫描实验确定 `minWorkers=1, energyThreshold=300`）：能量满（生产间歇）且至少 1 个基础劳动力后才投资；数量上限 = source 数（低数量）
- **产出调节**：矿工产出（掉落能量）由 deliver 执行者拾取（pickup 优先于自采）——源侧动态的一部分
- 部署参数可注入（`globalThis.__MINER_PARAMS`），参数扫描见 `scripts/param-sweep.ts`

### 5.3 分配问题形式化

每 tick，idle creep 集合 I 与可执行任务集合 J：

```
变量   x_ij ∈ {0,1}        creep i 是否执行任务 j
目标   max  Σ_i Σ_j x_ij · utility(i, j)
约束   Σ_j x_ij ≤ 1        每个 creep 至多一个任务
      （无任务人数上限）
```

求解策略（可插拔）：

| 策略                | 复杂度 | 说明                                                                       |
| ------------------- | ------ | -------------------------------------------------------------------------- |
| 贪心（本期）        | O(n·m) | 逐 creep 取当前边际效用最高任务；crowdingCost 按现有持有者数固定，近似最优 |
| 匈牙利算法          | O(n³)  | 精确解，n ≤ 12 时微秒级，需方阵化处理                                      |
| 线性规划（simplex） | 多项式 | crowdingCost 分段线性化后精确建模，需求解器依赖                            |

分配器以效用函数为参数，策略可替换，接口不变。

### 5.4 执行层控制：滞回状态机

能量状态是两态机（存于 `creep.memory.working`）：

```
采集中（!working）──满载──▶ 工作中（working）──耗尽──▶ 采集中
```

- **双阈值切换**：满载才转工作，耗尽才转采集；中间区间保持当前状态。
- **防振荡**：单阈值（满/空）会让消耗型动作（每 tick 耗 1-2 能量）在“干一次→回去采”间往返振荡；滞回让执行者在工作位置连续作业到能量耗尽。实测升级速率提升约 37 倍。
- **统一性**：动作在控制层面不分类——一次清空（transfer）与逐 tick 消耗（upgrade/build）都是“能量减少”，落在同一状态机内；新增动作直接复用 `isWorking`，无需切换逻辑。
- **状态延续**：转岗时状态语义天然兼容（能量耗尽转岗 → working=false → 直接采集），任务切换无需重置。

## 6. 稳态行为分析

### 6.1 冷启动（单房间，1 spawn，2 source）

```
t≈0    能量满 → 无 deliver 需求 → 出生 creep 领 upgrade
t≈小   生产消耗能量 → spawn 出现消耗速率 → deliver 需求声明 → 采集者就位
稳态    采集者数量随 rate 浮动：生产窗口多人（rate≈17），备产收敛（rate=10）
        剩余产能 → upgrade（边际效用均衡点）
```

### 6.2 能量满回收

结构能量满 → 需求消失 → 任务回收 → 采集者送完最后一趟后无任务可领 → 转 upgrade。全队产能平滑迁移，无瞬间停摆（每个执行者在其工作周期边界切换）。

### 6.3 震荡风险与阻尼

拥挤惩罚提供负反馈阻尼：执行者过多 → 边际效用下降 → 新执行者流向其他任务 → 人数回落。周期振荡幅度由 crowdingCost 斜率控制（斜率高 → 响应快、超调小）。

### 6.4 分配惰性（已修复，演进路径 7）

原缺陷：边际效用只在分配时点评估，生产窗口（rate 高）分配的多人 deliver 在窗口结束后不撤离，直到能量满，期间存在 ~100 tick 产能浪费。

现机制：**周期边界再评估**——任何执行者在能量耗尽（工作周期边界，不会每 tick 抖振）时，比较当前任务（去除自己后）的价值与其他任务最高价值，其他更高则释放重新分配。与原有转岗逻辑统一为同一机制。实测：生产窗口结束后 deliver 执行者自动回落，升级速率提升 ~18 倍。

## 7. 鲁棒性与失败模式

| 故障                          | 系统响应                                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------------ |
| creep 死亡                    | 持有者统计（每 tick 反查）自动剔除；其任务空出，下 tick 被重新分配                         |
| 任务目标消失（工地建成）      | 失效检测 → 任务回收 → 执行者重新分配                                                       |
| 需求频繁抖动（能量临界满/缺） | 声明层滞后（能量满 N tick 后才回收）可加，当前接受临界抖动（任务存在但执行者不换，影响小） |
| CPU 超限                      | 分配贪心 O(n·m)（n≤6, m≤12），声明/调度 O(m)；无求解器依赖                                 |
| 黑板损坏（Memory 结构异常）   | 任务 id 幂等、reconcile 自愈（需求重新声明后任务重建）                                     |

## 8. 演进路径

1. **storage/container/terminal**：新结构只需在声明层加入"可接收能量"列表——需求接口不变，调度/执行零改动
2. **挖矿（mine）**：新增 action + 映射表一行（WORK）+ 执行器一个——能力匹配让纯 WORK 矿工自然分流
3. **多房间**：声明层按房间遍历；分配的距离成本天然跨房间；战略层按房间任务效用决定扩张
4. **战斗/紧急事件**：紧急度注入（basePriority 覆盖或直接抢占黑板），优先级覆盖机制
5. **最优分配**：匈牙利/LP 后端替换贪心，效用函数不变（分配器接口已抽象）
6. **延迟需求**：需求可带“可延迟”标记（升级 vs 送能量），由效用权重表达时间敏感性
7. **周期边界再评估（分配惰性修复）✅**：任何执行者在能量耗尽（工作周期边界）时评估当前任务（去除自己）与其他任务的价值，其他更高则释放重新分配。生产窗口结束后多余采集者自动撤离（实测升级速率提升 ~18 倍）
